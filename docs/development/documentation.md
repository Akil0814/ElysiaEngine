# 文档维护规则

## 事实来源

现行文档必须能够对应到当前源码、配置或测试。不要用规划中的类型名描述已经实现的 API，也不要保留无法持续维护的源码行数、测试数量等快照统计。

## 放置规则

- 使用与运行说明放在 `docs/getting-started/`。
- 跨模块设计放在 `docs/architecture/`。
- 模块参考和指南放在 `docs/subsystems/`。
- 维护规范放在 `docs/development/`。
- 论文、课程材料和不再作为事实来源的发布物放在 `archive/`，不加入主导航。
- 不在源码目录中新增零散 Markdown；新文档必须从 `docs/README.md` 或对应子系统入口可达。

## 编写规则

- 标题和正文以中文为主，代码标识符保持源码拼写。
- 示例中的项目扩展使用 `Example*` 和 `example.*` 命名，避免绑定具体游戏。
- 明确区分当前实现、已知限制和目标设计。
- 文件迁移或重命名后同步修复相对链接与标题锚点。

## 提交前检查

1. 检查 Markdown 相对链接和图片引用。
2. 搜索过期项目名、旧路径和已经删除的类型。
3. 对照头文件确认示例签名和枚举值。
4. 运行 `git diff --check`、构建和完整 CTest。
