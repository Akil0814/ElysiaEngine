# 游戏开发必读：核心概念

无论你负责一个按钮、一个道具，还是整段关卡逻辑，都需要先知道代码放在哪里、什么时候执行，以及对象由谁管理。

## 场景、游戏对象与 UI 各负责什么

`Scene` 是一段运行内容的组织者，例如菜单或关卡。它持有场景对象，协调输入、更新与绘制。场景适合负责对象的组织和整体流程，不必承包每个对象的具体行为。

`GameObject` 表示游戏世界中的对象，例如角色、道具或装饰，提供世界矩形、绘制层级等基础。继承它不会自动获得移动、输入响应或物理碰撞，也不会自动参与逐帧更新；具体能力需要显式实现和接入。

`UiElement` 表示界面元素，走独立的布局与交互体系。

`UiElement`和 `GameObject` 都继承 `SceneObject`，共享活跃、可见、销毁等基本状态。

`UiElement`和 `GameObject` 二者区别在与 `GameObject` 会走摄像机投影变化但是 `UiElement` 只会被渲染在指定位置

比如一个游戏的局内道具

## 对象的归属与生命周期

对象成功加入场景后，由场景持有；加入 UI 容器的子节点由该容器持有。创建或添加接口返回的裸指针只是访问入口，不代表所有权。不要自行 `delete` 已交给场景或容器的对象，也不要再用另一个拥有所有权的指针管理它。

`destroy()` 只是标记销毁，不会在调用处立即释放内存。场景对象由场景的清理流程移除，UI 子节点由所属容器的清理流程处理。标记后应把它视为即将退出使用的对象，不依赖它暂时仍在内存中继续安排业务操作。

对象实际释放后，保存的裸指针不会自动变成空指针。只检查指针非空不能证明对象仍然有效；保存引用或让回调捕获对象之前，要明确谁负责解除引用，以及回调是否可能比对象活得更久。

场景的进入、退出、重置和销毁也是不同的事情。`on_enter()`、`on_exit()` 对应进入与离开，重置流程调用 `reset()`；退出场景不等于销毁场景实例，场景可以复用。重置具体恢复哪些状态由实现决定，也不能当成重新构造。

因此，重新进入场景时，不要默认道具数量已归零、旧对象已经清空或事件绑定已经解除。先确认当前场景的退出与重置逻辑，再决定自己负责的数据如何保留和清理。

## 代码什么时候执行

可以先用下面的简化流程理解正常运行的一帧；它不是全部内部调用的清单：

**输入处理 → 场景更新（普通更新、按需执行固定步、清理等）→ 渲染**

普通游戏对象需要实现 `Updatable` 并加入场景，才会被登记到相应的逐帧更新流程。仅仅写一个同名方法，或只继承 `GameObject`，都不会让引擎自动调用它。能否在当前帧执行，还取决于对象状态和暂停规则。

逐帧更新中的 `delta` 表示时间增量，单位为秒。涉及速度或计时的普通逻辑应按经过的时间计算，而不是假定每帧耗时相同。例如每秒变化的数量，应结合 `delta` 累积，避免效果随帧率改变。

固定步更新按固定时间间隔推进。某一帧可能不执行固定步，也可能执行多次，不能把它理解为“每帧恰好调用一次”。物理相关任务应遵循对应专题的固定步规则，不要在逐帧更新和固定步中重复推进同一份状态。

渲染负责呈现当前状态。不要在提交绘制内容时发放奖励、推进计时或消费输入，否则游戏规则就会依赖绘制是否发生。

## 容易混淆的状态与坐标

**可见**决定是否参与相应绘制，并不等于是否继续更新。隐藏一个道具，不会自动完成拾取判定或停止它的业务行为。

**活跃**用于筛选相应的更新和输入流程，并不等于不可见。以普通游戏对象为例，场景绘制检查可见与销毁状态，不把活跃状态直接作为绘制开关。也不要把活跃开关当成物理、UI 等所有子系统的通用禁用接口。

**暂停**有自己的规则：场景会跳过不允许暂停时更新的对象，并停止该场景的物理推进；允许暂停时工作的对象仍可运行。输入是否在暂停时处理也有单独规则，不能推断整个程序已经静止。

**销毁**表示对象准备退出使用，与隐藏、停用不同。临时隐藏与永久移除应选择不同操作。

世界坐标描述角色和道具在游戏世界中的位置，屏幕与 UI 坐标用于输入和界面显示，UI 还受所属容器布局影响。不要直接拿鼠标位置与道具的世界矩形比较；先确认输入坐标的含义，并使用对应的坐标转换。

逻辑位置和显示位置也可能不同。`world_rect()` 表示对象的世界矩形，`render_rect()` 可以包含物理插值产生的显示偏移。游戏规则应使用逻辑状态，不把为了平滑显示而计算的位置写回业务状态。

## 完成一个小任务时如何划分职责

以“拾取道具并更新数量”为例：场景组织角色、道具和界面；道具维护是否已被领取；游戏规则确认拾取结果并更新数据；UI 展示新数量；音频通过已有服务请求播放。这个例子说明职责划分，不规定必须采用某一种事件或回调机制。

对象承载某个实例的状态；共享服务提供可复用能力；资源是这些能力使用的纹理、音频、配置等内容。销毁一个道具，不代表要释放所有道具共享的纹理。使用资源前应确认它已按项目流程加载，不要绕过既有资源管理方式自行管理共享内容。

如果你只负责数量显示，重点是数据从哪里来、何时刷新以及界面失效后如何解除关联；不需要先掌握碰撞和音频的全部 API。接着到[按开发任务查阅](README.md#按开发任务查阅)选择相关专题即可。

动手前，用四个问题检查自己的设计：

1. 这段逻辑归场景、对象、UI，还是普通业务数据？
2. 它何时执行，是事件触发、逐帧更新，还是固定步更新？
3. 谁拥有这些数据或对象，谁负责释放？
4. 离开场景或销毁对象后，保存的引用与回调是否仍然有效？
