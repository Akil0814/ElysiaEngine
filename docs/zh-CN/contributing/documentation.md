# Elysia Engine 文档维护规则

本文档规定 Elysia Engine 的文档组织、编写和维护约定，适用于新增、修改及删除项目文档的开发者。

文档应准确反映项目当前状态，帮助开发者理解引擎、使用公开接口及参与开发。

## 1. 文档分类

项目文档按照用途分为以下四类。

| 分类 | 内容 |
| --- | --- |
| 使用指南 | 构建运行、核心概念、公开 API、子系统使用方法及示例 |
| 架构文档 | 当前引擎的模块职责、依赖关系、内部设计与运行机制 |
| 开发与贡献指南 | 编码规范、测试流程、开发约定及文档维护规则 |
| 设计文档 | 开发路线、设计提案、计划中的功能及待完成的架构迁移 |

### 使用指南

面向使用 Elysia Engine 开发游戏的开发者。

应重点说明：
- 引擎提供什么功能。
- 如何正确使用公开接口。
- 必须遵守的接口契约和生命周期约定。
- 常见错误及其处理方式。

使用指南不应依赖读者理解引擎内部实现。

### 架构文档

面向希望了解、维护或扩展引擎的开发者。

应描述当前代码的实际设计，包括模块职责、依赖关系、关键数据结构、执行流程及设计约束。

架构文档应反映当前实现，而不是尚未落地的目标设计。

### 开发与贡献指南

面向参与引擎开发及维护的开发者。

记录项目统一的开发要求，包括代码规范、测试方式、文档维护及其他贡献约定。

### 设计文档

用于记录未来规划、设计提案及尚未完成的迁移工作。

除非明确标记为当前实现参考，否则设计文档中的类型、接口和流程均不代表已实现的功能或稳定的 API 承诺。

计划中的功能不得仅因存在设计文档，就被描述为引擎当前支持的能力。

## 2. 文档内容要求

### 准确性

文档应以当前源码、测试和实际配置为事实依据。

- 不得将计划中的功能描述为已实现。
- 不得将尚未确定的接口描述为稳定 API。
- 不得根据过时的实现推断当前行为。
- 不得声明未经验证的平台兼容性或性能表现。
- 不得省略会影响正确使用接口的重要限制。

当文档与实际实现不一致时，应检查实现和测试，确认预期行为后修正文档或代码。

### 明确适用范围

文档应根据目标读者选择合适的内容深度。

使用指南侧重调用方式和接口契约；架构文档侧重设计原因与内部运行机制。

不必在多个文档中完整重复相同内容。对于已有的详细说明，应通过链接引用。

### 接口与生命周期

涉及公开 API 时，应根据需要说明：

- 接口的用途及调用前提。
- 参数与返回值的含义。
- 对象所有权及引用的有效期。
- 错误处理与失败语义。
- 调用时机、执行顺序及其他重要限制。

尤其是涉及对象创建、场景切换、延迟销毁和资源释放的接口，不应仅依赖函数名称解释其行为。

### 代码示例

代码示例应与当前公开接口保持一致。

- 使用当前有效的类型、函数和参数。
- 明确示例所需的初始化条件。
- 避免使用已废弃或仅供内部使用的接口。
- 需要省略代码时，应确保省略部分不会造成误导。

标记为完整示例的代码应能够在声明的环境下构建和运行。

仅用于展示局部调用方式的代码片段，不要求独立编译，但应明确其必要上下文。

## 3. 文档组织与命名

### 文件组织

新文档应放入与其用途对应的目录。

- 使用说明放入使用指南。
- 当前实现说明放入架构文档。
- 开发规范放入贡献指南。
- 尚未实现的设计放入设计目录。

子系统的相关文档应尽可能集中管理，避免同一模块的说明分散在无关目录。

### 文件命名

Markdown 文档统一使用 `.md` 扩展名。

建议采用小写英文及连字符命名，例如：

- `coding-standard.md`
- `build-and-run.md`
- `core-concepts.md`

目录入口使用 `README.md`。

已有文件不必仅为了统一命名而进行无意义的重命名。

### 文档入口

新增文档时，应在对应目录的 `README.md` 中提供入口。

如果文档涉及其他分类，可在相关文档中添加交叉引用。

不要求将所有文档直接列入项目根 README。

## 4. Markdown 编写规范

### 标题

- 每份文档使用一个一级标题 `#`。
- 主要章节使用二级标题 `##`。
- 子章节依次使用三级及更低级标题。

### 链接

仓库内部文档及源码优先使用相对路径。

链接应指向实际存在的文件，并在文件移动或重命名时同步更新。

不得在正式文档中保留无效链接或未完成的占位符，例如：

`[使用指南](...)`

对于尚未编写的文档，应先完成对应内容，或暂时使用不包含链接的文字说明。

### 代码块

代码块应尽可能标记语言类型，例如：

```cpp
ELYSIA_LOG_INFO("Gameplay", "Game initialized.");
```

```powershell
ctest --test-dir build -C Debug --output-on-failure
```

命令示例应明确适用的平台、构建配置及必要前提。

### 图片

图片应存放在仓库内合适的资源目录，并通过相对路径引用。

图片应提供有意义的替代文本。

修改涉及截图的功能后，应检查对应图片是否仍然反映当前界面。

## 5. 文档更新要求

文档应与相关代码变更同步维护。

以下改动需要检查并更新相关文档：

| 改动类型 | 需要检查的文档 |
| --- | --- |
| 新增或修改公开 API | 使用指南、API 参考 |
| 修改接口契约或错误处理行为 | 使用指南、架构文档 |
| 修改对象生命周期或执行顺序 | 核心概念、相关子系统文档 |
| 修改模块结构或依赖关系 | 架构文档 |
| 修改构建选项或工具链要求 | 构建指南 |
| 修改测试目标或测试流程 | 测试指南 |
| 新增已实现功能 | 使用指南、架构文档、Roadmap |
| 完成设计提案的实现 | 设计文档、架构文档、Roadmap |

并非每次代码修改都必须更新文档。

对于不改变公开行为、架构或开发流程的内部实现调整，可不修改文档。

但如果改动使现有文档不再准确，应在同一变更中修正。

## 6. Roadmap 与设计文档维护

Roadmap 用于记录功能开发状态，不承担详细设计说明的职责。

设计方案应放入独立文档，并在 Roadmap 中按需提供链接。

当功能状态发生变化时，应同步更新 Roadmap。

功能实现完成后，应：

1. 确认实现与测试状态。
2. 将当前使用方法写入使用指南。
3. 将实际架构写入架构文档。
4. 更新 Roadmap 中的功能状态。
5. 检查原设计文档是否需要标记为已实现、部分实现或已废弃。

不应直接将设计提案视为最终实现文档。

如果最终实现与原设计不同，应在相关文档中反映实际情况，避免读者误用过时接口。

## 7. 多语言文档

不同语言版本应尽可能保持技术内容一致。

涉及公开接口、功能状态、生命周期及重要限制的修改，应检查其他语言版本是否需要同步更新。

代码标识符、文件路径、宏名称和 API 名称应保持与源码一致，不应为了翻译而修改。

如果某个语言版本尚未完成更新，应避免继续提供可能误导读者的过时说明。

不要求所有文档在首次创建时都同时提供多语言版本。

## 8. 提交前检查

提交文档变更前，应确认：

- [ ] 文档位于正确的分类与目录。
- [ ] 内容与当前代码、测试及配置一致。
- [ ] 未将计划中的功能描述为已实现。
- [ ] 代码示例使用当前有效的接口。
- [ ] 内部相对链接及图片路径正确。
- [ ] 新增文档已加入对应目录的索引。
- [ ] 相关 Roadmap 和设计文档已按需更新。
- [ ] 其他语言版本已按需检查。
- [ ] 不存在未完成的占位符或明显过时的说明。

涉及功能变更的文档，应与对应代码和测试一起提交。

文档维护的目标是保证内容准确、可查找、可持续维护，而不是追求篇幅或重复记录源码中的每一个实现细节。
